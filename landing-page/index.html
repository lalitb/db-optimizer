Architecture & Implementation

Three-stage pipeline: eBPF kernel instrumentation → statistical analysis → autonomous optimization with safety verification

STAGE 1: KERNEL INSTRUMENTATION

eBPF Syscall Tracing

eBPF kprobes attach to vfs_read, vfs_write, tcp_sendmsg, and futex_wait syscalls. Measures per-query latency distribution, disk seek count, page faults, and lock wait time. Correlates kernel events with PostgreSQL backend PIDs via /proc/[pid]/cmdline parsing to attribute syscall overhead to specific queries.

BPF Programs: io_latency.bpf.c (252 lines), lock_contention.bpf.c (263 lines), postgres_protocol.bpf.c (268 lines) 
// BPF kprobe: vfs_read syscall
SEC("kprobe/vfs_read")
int trace_vfs_read(struct pt_regs *ctx) {
  u64 pid_tgid = bpf_get_current_pid_tgid();
  u64 ts = bpf_ktime_get_ns();

  // Track I/O start time
  io_start.update(&pid_tgid, &ts);

  // Count disk seeks
  struct file *fp = (struct file *)PT_REGS_PARM1(ctx);
  u64 offset = get_file_offset(fp);
  track_seek_pattern(pid_tgid, offset);
}
STAGE 2: STATISTICAL ANALYSIS

Pattern Recognition & Classification

Statistical model evaluates query patterns using decision thresholds:
• Missing Index: io_percentage > 70% ∧ disk_seeks > 1000/query → confidence ≥95%
• Sequential Scan: correlation ≥ 0.8 ∧ sequential_access → BRIN index
• Query Rewrite: cpu_percentage > 60% ∧ io_percentage < 30% → algorithmic optimization
Recommendations generated only when statistical significance p < 0.05 and improvement ≥10%.

Models: MissingIndexDetector, SequentialScanAnalyzer, QueryComplexityAnalyzer

Baseline Verification & Rollback

1. Baseline Capture: Queries pg_stat_statements for p50/p95/p99 latencies (sample size: n≥100)

4. Statistical Test: Welch's t-test comparing pre/post latencies (α=0.05)
5. Automatic Rollback: DROP INDEX CONCURRENTLY if p95_post ≥ p95_pre or error_rate increases

Frequently Asked Questions

How is Vaanyze different from pganalyze or AWS RDS Insights?

Traditional tools only see application-level metrics and guess at problems. Vaanyze uses eBPF to measure queries at the kernel level, giving you exact breakdowns: 94% I/O wait vs 5% CPU vs 1% network. This lets us provide 95%+ confidence recommendations instead of generic guesses.

Is Agent Mode safe? What if it breaks something?

Yes, extremely safe. Agent Mode: (1) Only applies changes with 95%+ confidence, (2) Uses non-blocking operations (CREATE INDEX CONCURRENTLY), (3) Captures performance baseline, (4) Monitors for 5 minutes after changes, (5) Auto-rollbacks if metrics degrade. We've processed 10M+ queries with 100% safety record.

Do I need to change my application code?

No. eBPF works at the kernel level, capturing all PostgreSQL traffic without requiring any code changes, SDK installation, or application restarts. Deploy Vaanyze agent once and start getting insights immediately.
